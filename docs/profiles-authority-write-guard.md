# 프로필 관리자 권한 조작 차단

## 이번 긴급 패치의 범위

- 일반 회원의 `profiles.role` 변경과 관리자 권한을 지정한 INSERT/UPSERT를 DB에서 거절한다.
- 기존 프로필의 `id`, `user_id` 변경과 다른 회원 소유의 프로필 생성을 차단한다.
- 화면에서 버튼을 숨기는 방식이 아니므로 직접 REST 요청에도 적용된다.
- 실제 DB 실행 역할을 검사한다. 회원이 수정할 수 있는 프로필이나 메타데이터를 신뢰하지 않는다.
- 기존 회원 데이터, 정상 관리자 권한, 매칭·결제·사진·연락처 공개 조건은 변경하지 않는다.
- 기존 인증 서버의 회원 권한 UPDATE와 service-role UPDATE를 모두 유지한다.

**이 SQL은 모든 민감 필드의 쓰기 권한을 강화하는 패치가 아니다.**
현재 배포된 휴대폰 인증 동기화가 회원 권한으로 저장하므로 `phone_*`를 동시에 막지 않는다.
휴대폰·밴·결제성 필드의 직접 수정 차단은 서버 저장 경로를 먼저 전환하고 별도로 검증해야 한다.
진행 중인 `profile_phone_verification_atomic_completion.sql` 및 인증 API 변경과 혼합 배포하지 않는다.

## 적용 및 확인

1. 운영 환경의 기존 `profiles_read_owner_boundary` 읽기 정책과 INSERT/UPDATE 트리거를 확인한다.
2. 오프라인 검사 `scripts/check-profiles-authority-write-guard.cjs`를 실행한다.
   `PRIVACY_TEST_PGLITE_PATH`에는 별도 설치한 `@electric-sql/pglite` 모듈 경로를 지정한다.
3. DB 소유자가 `supabase/sql/profiles_authority_write_guard.sql`을 실행한다.
   한 트랜잭션이며, 잠금 대기는 5초로 제한한다. 실패하면 적용되지 않는다.
4. `supabase/sql/profiles_authority_write_guard_verify.sql`로 설치 상태를 읽기 전용 검증한다.
5. 본인 프로필 조회·기존 승인 매칭 연락처 조회를 확인한다. 검증 목적으로 실제 회원의
   관리자 승격, 결제, 문자 발송 또는 번호 변경을 하지 않는다.

GitHub 반영이나 앱 빌드만으로 DB에는 적용되지 않는다. 운영 SQL 실행 및 확인 전에는
운영 취약점을 차단했다고 안내하지 않는다. 기존에 누군가 권한을 조작했는지 여부는
별도 로그/권한 검토가 필요하며, 이번 패치가 과거 노출 여부를 입증하지는 않는다.

## 안전성 검사

동일한 읽기 정책과 레거시 쓰기 정책을 갖춘 독립 PostgreSQL(PGlite)에서 가짜 데이터로
패치 전 번호 조회 우회를 재현하고 패치 후 차단을 확인한다. 신규 가입, INSERT/UPSERT,
NULL·ID 변조, 메타데이터 위장, 기존 인증 저장, 설정 저장, 정상 관리자 및 서버 연락처
조회, 반복 적용을 검사한다. 테스트는 운영 DB에 연결하지 않는다.

패치 후 정상 기능에 문제가 있으면 실패한 요청과 실제 실행 역할을 확인해 좁게 수정한다.
관리자 권한 필드를 다시 누구나 수정하도록 열거나 읽기 제한을 해제하지 않는다.
