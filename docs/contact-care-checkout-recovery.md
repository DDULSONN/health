# 교환권 사용 시 만료 결제 대기 복구

## 확인한 원인

2026-10-28 제보에서 토스 주문은 `EXPIRED`이며 승인 시각이 없었으나,
사이트 주문은 `ready`로 남아 기존 교환권 RPC가 `CARE_CHECKOUT`으로 거절했다.
결제창을 열고 완료하지 않은 기록도 기한 없이 차단하던 문제다.

## 변경 범위

- `contact-care` POST의 기존 교환권 RPC가 정확히 `CARE_CHECKOUT`으로 실패한 경우만 처리한다.
- 해당 매칭 양측의 차단 원인 주문을 최대 9건 읽고 8건 이하일 때만 결제사 조회를 진행한다.
- 모든 원인 주문이 미승인 `ready`이고, 토스의 동일 주문번호·금액에서 `EXPIRED` 또는 `ABORTED`가 확인되어야 한다.
- 결제키·승인·환불 증거, 다른 소유자, 알 수 없는 상태, 타임아웃, 404는 자동 해제하지 않는다.
- 확인된 주문만 조건부 갱신으로 로컬 `canceled` 상태로 정리한다. 결제사 승인·취소·환불 API는 호출하지 않는다.
- 원래 RPC를 한 번만 다시 호출한다. 기존 SQL의 매칭 잠금·보유량·차단·인증·상태 확인과 원자적 번호 공개/차감은 유지한다.
- 조회 실패, 사용 완료, 권한 오류, 다른 RPC 실패에서는 재시도하지 않는다.
- 새 SQL은 필요 없다. 앱 서버 패치 배포가 있어야 모든 회원에게 자동 복구가 적용된다.

## 검증

### 2026-10-29: 만료 후 화면 복구

- `CARE_CHECKOUT`으로 막힌 해당 매칭만, 펼친 화면이 보이는 동안 1분 간격으로 다시 확인한다. 접힘·다른 상대 선택·백그라운드에서는 자동 조회하지 않는다.
- ‘내역 다시 확인’도 같은 상태 확인을 수행한다. 진행 중·조회 불명 상태는 계속 보호하며 고객센터 요청 없이 만료 후 사용 버튼을 다시 열 수 있다.
- 별도 `check_checkout` POST는 로그인·동일 출처·매칭 참여자·미사용 교환권을 확인한 뒤 기존 만료 확인 함수를 호출한다. 일반 GET은 변경하지 않는다.
- 상태 확인은 교환권 사용 RPC, 결제 승인/취소, 번호 공개를 호출하지 않는다. 자동 복구 후에도 회원이 상대를 확인하고 사용을 승인해야 한다.
- 승인·환불·금액 불일치·조회 실패에 대한 기존 차단 및 실제 사용 시 SQL 잠금/재검증은 유지한다. 새 SQL·정기 작업은 필요 없다.

`scripts/check-contact-care.cjs`에서 실제 API 핸들러와 로컬 PostgreSQL을 연결해 검증한다.
결제사 응답만 모킹하며 실결제·환불은 발생시키지 않는다.

- 일반/관리자 추가 지급 교환권의 만료 주문 복구와 재호출 멱등성
- 진행·입금 대기·승인·환불·알 수 없는 상태와 번호/금액 불일치
- 타임아웃·404·503에서 교환권 보존
- 조회 도중 결제 승인/새 주문/차단 발생 시 중복 교환 방지
- 양측 주문 검사, 8건 조회 제한, 새 주문 생성 금지, 기존 결제 기록 보존
- 기존 인증·차단·보상·복수 교환권·연락처 공개 회귀 검사

2026-10-28 제보 주문 1건은 결제사에서 만료를 재확인한 뒤 로컬 대기 상태만 정리했다.
원래 보상권은 캡처 이후 다른 매칭에서 이미 사용된 상태였으며,
해당 보상권 및 두 매칭의 공개·사용 기록은 수정 전후 동일함을 확인했다.
추가 교환권 지급이나 기존 교환 취소는 하지 않았다.
