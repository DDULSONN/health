# 복귀 회원 프로필 작성 지원권

## 대상과 지급 조건

- 이번 캠페인 시작 시점에 대상자를 한 번 확정한다. 기준은 한국 시간 기준 3개월 전(90일 고정이 아닌 달력 기준) 이후 저장된 활동이 없는 일반 회원이다.
- 로그인(`auth.users.last_sign_in_at`), 세션 생성·갱신(`auth.sessions`), 의미 있는 활동(`profiles.last_meaningful_activity_at`), 프로필 생성·후보 새로고침, 작성 퍼널의 기록 중 가장 최근 시점을 사용한다. 과거 모든 방문의 완전한 로그는 아니므로 **실제 미방문을 전수 증명하는 통계로 사용하면 안 된다.** 최근 기록이 하나라도 있으면 제외한다.
- 신규 계정, 관리자, 밴/탈퇴 계정, 현재 유효한 1:1 프로필(`submitted/reviewing/approved`) 보유자는 제외한다. 오픈카드만 있는 장기 미활동 회원은 포함할 수 있다.
- 복귀 로그인으로 활동 시간이 바뀌어도 이미 확정된 자격은 유지된다. 활성화 SQL을 다시 실행해도 새로운 대상을 추가하지 않는다.
- 휴대폰 인증과 **캠페인 시작 이후 새 1:1 프로필 등록**이 완료되면 계정당 한 번 추가 지원권 5장 지급. 사진 2장과 정상 활성 상태를 DB에서 재확인한다. 통합 작성에서는 1:1을 함께 등록해야 하며, 오픈카드 단독 작성이나 기존 1:1 수정은 대상이 아니다.
- 기존 보유 지원권에 더하며, 평일/주말 기본 횟수·매칭 추천·번호 교환·사진 공개 정책은 바꾸지 않는다.
- 새 계정은 고정 대상자에 없으므로 탈퇴/재가입으로 이 캠페인을 재수령할 수 없다. 다른 정상적인 지원권 혜택과는 합산된다.

## 안전한 적용 순서

1. `supabase/sql/return_profile_reward.sql` 설치: 신규 테이블·함수만 설치한다. 안내와 지급은 기본 비활성, 회원 적립 없음. **운영에 아직 실행하지 않은 파일이다.**
2. 코드를 배포하기 직전에 운영자 확인 후 `supabase/sql/return_profile_reward_activate.sql` 실행: 대상 스냅샷을 1회 저장하고 활성화한다. 이 작업 자체는 지원권을 지급하지 않는다. 로그인한 뒤 대상 선정을 하면 활동 시간이 바뀌므로, 대상 회원의 복귀 안내/유입 전에 확정해야 한다.
3. 검증된 코드를 배포한다. 활성화와 공개 사이의 간격을 최소화한다. 코드만 배포하거나 SQL만 설치한 경우 안내·지급이 꺼져 있는 것은 정상이다.
4. 실제 등록/적립은 운영자가 승인한 테스트 계정으로 별도 확인한다. 로컬 검증은 가상 데이터이며 실제 회원 지원권·프로필은 변경하지 않는다.

운영 상태 확인(이메일·전화번호 조회 불필요):

```sql
select campaign_key, enabled, activated_at, inactivity_cutoff
from public.return_profile_reward_campaign;

select count(*) as eligible_members,
       count(rewarded_at) as rewarded_members,
       count(rewarded_at) * 5 as granted_credits
from public.return_profile_reward_members;
```

중단은 캠페인 행만 변경한다. 이미 지급한 지원권은 회수하지 않는다. 회원 테이블/지급 이력을 지워서는 안 된다.

```sql
update public.return_profile_reward_campaign
set enabled = false where campaign_key = 'return-profile-2026-10';
```

## 처리 방식과 한계

- `GET /api/return-profile-reward`는 본인 상태만 읽는다. 요청에 회원 ID/수량/기준일을 받지 않고, 서버가 인증된 사용자 ID를 사용한다. 개인별 응답은 `private, no-store`다.
- 등록 API가 성공한 후 `after()`에서 지급을 시도한다. 지급 장애가 등록 성공을 실패로 바꾸거나 프로필을 삭제하지 않는다.
- 다음 대상 화면 진입 시 상태를 조회하고 `ready`면 본인 `POST`로 재확인한다. 지급 장애 때 다시 작성할 필요 없이 배너의 `지급 다시 확인`으로 재시도한다. 등록 직후 탭을 닫고 서버 지급도 실패했다면 다음 방문/재시도까지 지급이 지연될 수 있다.
- 지급 함수는 캠페인 → 회원 지급 행 → 회원 프로필 → 등록 카드 → 지원권 잔액 순서로 잠그며, 지원권 증가·0원 주문 기록·지급완료 표시를 한 트랜잭션으로 처리한다. 실패 시 모두 롤백된다. 기존 가입/결제/프로필 테이블에 새 트리거를 달지 않는다.
- 새 테이블/함수는 브라우저 `anon/authenticated` 접근 불가. 서버 `service_role`만 조회/지급 실행 가능하며 직접 지급 상태 수정 권한은 없다.
- 안내는 홈/매칭/마이페이지/통합작성에만 작게 표시한다. 닫기는 세션 내 상태별로 유지되고, 닫았던 대상도 실제 지급 완료 시 확인 안내를 볼 수 있다. 로그아웃/계정 변경 시 이전 응답은 폐기한다.
- 반복 타이머/크론/메일 발송 없음. 대상 선정은 한 번 집계하고, 이후 본인 PK 조회다. 대상이 아닌 회원의 빈 응답은 컴포넌트 생명주기 동안 메모하여 화면 이동마다 반복 조회하지 않는다. 최초 인증 상태 확인과 대상자의 경로 이동에는 소량의 추가 요청이 있다.

## 로컬 검증

```text
node --require ./scripts/test-no-network.cjs --test scripts/check-return-profile-reward.cjs
node scripts/check-return-profile-reward-browser.cjs
npm run build
```

SQL 검증은 운영에 연결하지 않는 PGlite PostgreSQL 엔진을 사용한다. 중복 요청·반복 지급·잔액 유지·후속 SQL 실패 롤백·권한·밴/탈퇴·정확한 3개월 기준·활성화 재실행·중단 상태를 점검한다. PGlite의 병렬 요청은 내부적으로 직렬 처리되므로 운영 PostgreSQL의 다중 연결 부하 시험을 대체하지는 않는다.

화면 검증은 실제 배너 컴포넌트와 가상 인증/API를 사용한다. 모바일 320/390px, 태블릿/데스크톱, 닫기, 오류 재시도, 계정 전환, 늦은 응답, 세션 저장 차단을 점검한다. 미리보기는 `node scripts/preview-return-profile-reward.cjs` (기본 3142 포트). 모든 지급은 가상이다.
