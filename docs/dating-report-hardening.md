# 프로필 신고 보강

## 수정 범위

- 오픈카드 상세, 홈 1:1 후보/진행 매칭, 마이페이지 받은·보낸 지원/후보/매칭 기록의 신고창을 공통 컴포넌트로 통일한다.
- 빠져 있던 홈 1:1 신고 버튼과 마이페이지 보낸 오픈·유료 지원 상대 신고 버튼을 추가한다.
- 신고 사유 선택, 한글 상세 입력, 중복 클릭 방지, 모바일 스크롤, 접수 결과 안내를 제공한다.
- 카드 신고에 Origin/UUID 검사를 추가하고, 사용자 신고의 잘못된 사유·대상 조회 오류를 구분한다.
- 중복 요청은 기존 신고 사유/증거/처리 상태를 덮어쓰지 않는다. 기존 신고가 확인된 경우에만 중복 접수로 응답한다.
- 신고 저장과 차단/대기 요청 정리 결과를 구분한다. 후속 작업 실패를 접수 실패로 잘못 안내하지 않는다.
- 차단 후 정리 대상은 미결제·미공개인 proposed/source_selected/candidate_accepted 상태뿐이다. 쌍방 수락, 결제 처리, 번호 공개 완료 건은 이 경로에서 취소하지 않는다.
- 관리자 신고 API는 기존 관리자 허용 목록 기반 공통 인증을 사용한다. 상태 필터를 DB에서 먼저 적용하고 50건씩 페이지를 나눈다. 지연된 이전 목록 응답은 무시한다.
- 관리자 1:1 신고 목록에 매칭 이름과 계정 닉네임을 함께 표시한다.
- 신고 정지 처리 실패 시 신고가 먼저 처리 완료되는 순서 오류를 수정한다.
- 증거는 공개 프로필 문구 등 명시한 필드만 보관한다. 전화번호/이메일/인스타 계정/사진 저장 경로를 통째로 복사하지 않는다. 다시 보존할 때 원본을 유지하고 최신 내용은 별도로 저장한다.

## 운영 반영 순서

1. 먼저 코드 배포와 서버 준비 완료를 확인한다.
2. 그 다음 Supabase SQL Editor에서 `supabase/sql/dating_report_evidence_columns.sql`을 실행한다.
3. 관리자 신고함에서 증거 DB 업데이트 안내가 사라지는지 확인한다.

증거 컬럼이 없는 기존 DB에서도 신고 접수와 상태 처리는 계속 동작한다.
이때 증거 보존 버튼은 비활성화하고 필요한 업데이트를 명시한다.
새 SQL은 신고 테이블 컬럼만 추가하며 회원/휴대폰 인증/결제/매칭/RLS 설정은 변경하지 않는다.
기존 신고 당시 저장되지 않은 프로필의 원래 내용은 소급 복원할 수 없다. 관리자 재보존은 현재 남아 있는 내용을 기준으로 한다.

## 검증

- `npm run check:dating-reports`: 독립된 가짜 DB로 API 회귀 테스트. 실제 신고/차단/정지/문자/결제 실행 없음.
- `REPORT_TEST_PGLITE_PATH`에 설치된 `@electric-sql/pglite` 경로를 지정하면 추가 SQL 재실행/데이터 보존 테스트도 실행한다.
- `node scripts/preview-dating-reports.cjs`: 127.0.0.1:3138 전용 UI 테스트 서버. 실제 공통 컴포넌트와 사이트 CSS를 쓰며 API는 가짜 응답만 반환한다. 상세 내용에 '차단실패'를 입력하면 부분 실패 화면을 확인할 수 있다.
- 2026-09-09 검증: SQL 테스트 포함 49개 통과, TypeScript 및 프로덕션 빌드 통과. 390px 브라우저에서 한글 입력/사유 선택/접수 중 비활성화/완료 및 차단 실패 안내 확인.

수정은 신고 흐름에 한정한다. 번호 인증 API, 결제 승인 로직, 추천 알고리즘, 사진 제공 로직은 이번 패치 대상이 아니다.
실제 운영 회원에게 테스트 신고·차단은 하지 않았다. 운영 코드/SQL 적용 후 실사용 환경 확인은 별도로 필요하다.
