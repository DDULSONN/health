# 가입·작성 현황 및 오류 화면 복구

## 범위와 적용 상태

- 기준 커밋: d2fa9e8. 전용 작업 브랜치: codex/funnel-error-recovery.
- 관리자 마이페이지 → 관리 → 소개팅 통계 상단에 현황 패널을 추가한다. 해당 탭을 열 때만 불러온다.
- 초기 구현/검증은 로컬에서 진행했다. 실회원, 실제 결제/인증/메시지는 변경하지 않았다.
- 통계 활성화에는 별도 `supabase/sql/onboarding_funnel.sql` 적용이 필요하다. 적용 전에는 '통계 저장 설정 미적용'으로 표시하며 수집 오류는 기존 기능을 막지 않는다. 운영 확인 결과는 아래에 기록한다.

## 수치의 의미

- 오늘/최근 7일/최근 30일 **한국 시간 가입 코호트의 현재 상태**. 날짜는 auth.users.created_at 기준이며 profiles가 존재하는 계정만 포함한다.
- 탈퇴 계정과 DB role=admin을 제외한다. 기존 운영 현황의 profiles.created_at 기준 가입 수와 정의가 다를 수 있다.
- 중복 프로필/매칭이 있어도 회원 한 명은 단계별 한 명으로 집계한다. 이전 단계 조건을 충족한 회원 중 다음 단계 완료 수를 표시한다.
- 프로필 등록은 DB에 오픈카드 또는 1:1 기록이 하나 이상 있는 경우다. 공개/승인 여부나 소개글 품질 점수가 아니다. 이후 단계는 1:1 등록 → 현재 mutual_accepted → contact_exchange_status=approved 기준이다.
- 취소/삭제로 현재 상태가 바뀌면 수치가 감소한다. 누적 성공 이력, 광고 전환 귀속, 실제 대화 여부를 나타내지 않는다.
- 인증/통합 작성 화면 기록은 고정 코드의 최초 발생만 저장한다. 방문 단계/오류 안내를 본 회원 수이지 오류 발생 횟수가 아니다. 원인 확정이나 미등록=이탈로 해석하지 않는다.
- 수집 시작 전, 기존 별도 작성 화면, 차단된 전송은 화면 통계에 없다. 서버 등록 수와 화면 기록 수는 서로 다른 데이터다.

## 데이터와 권한

- 새 테이블은 내부 회원 ID, 허용된 진단 코드, 서버 최초 기록 시각만 저장한다. 코드 18개로 회원당 최대 18행.
- 입력 내용, 닉네임, 이메일, 번호, 인증번호, 사진/파일 경로, 오류 원문, URL, IP를 저장하거나 출력하지 않는다.
- auth로 확인한 회원 ID만 사용한다. 외부 origin/미로그인/큰 본문/추가 필드/임의 코드는 버린다.
- 클라이언트 단계 전송은 동기 대기/재시도 없이 best effort. 계정별 메모리 중복 방지, 서버 인스턴스별 분당 30회 제한, DB 기본키 중복 방지. 분산 전체 공격 차단을 보장하는 전역 제한은 아니다.
- 회원 프로필 삭제 시 FK cascade로 진단도 삭제된다. 계정이 유지되는 동안 최초 기록은 남는다. 개인별 내용을 표시하는 관리자 기능은 없다.
- anon/authenticated는 테이블 접근 및 집계 함수 실행 불가. 서비스 키로 집계하되 관리자 API가 서버의 관리자 허용 목록을 먼저 검사한다.
- 기존 매칭/번호 인증/결제 테이블, RLS, 함수, 트리거는 수정하지 않는다. 집계는 읽기 전용, 추가 cron/외부 분석 SDK 없음.
- SQL은 트랜잭션 및 잠금 대기 제한이 있으며 재실행해도 수집 시작 시각을 덮어쓰지 않는다.

## 오류 복구

- app/error.tsx + global-error.tsx가 예기치 않은 렌더 오류를 사이트 톤의 복구 화면으로 처리한다. 루트 레이아웃/스타일이 실패해도 기본 UI가 표시되도록 인라인 스타일과 일반 링크를 쓴다.
- 확인된 조회 화면에서만 사용자가 누르는 '화면 다시 불러오기'를 제공한다. 자동 재시도 없음.
- 결제 완료 콜백, 인증 콜백, 가입/탈퇴, 프로필 제출, 기타 처리 화면에서는 reset을 제공하지 않고 내역 확인을 안내한다. 결제 승인/지원/OTP POST를 호출하는 코드가 없다.
- 문의 내용에는 안전한 서버 digest 또는 시각 기반 코드, 화면 분류, 발생 시각만 포함한다. error.message/stack, 전체 URL/query는 포함하지 않는다.
- 복사 권한 거절 시 직접 선택할 수 있는 텍스트를 제공한다. 이메일은 사용자가 직접 보내는 링크이며 자동 발송하지 않는다.
- 모든 네트워크/이벤트 핸들러 오류를 자동 수집하는 모니터링은 아니다. 기존 API 실패 처리는 유지한다. 문의 코드는 진단 도움 정보이며 새 서버 로그 수집 기능은 아니다.

## 검증

- 새 단위/API/변경 범위 검사 66건 통과. 원문/임의 사용자 주입, origin, 크기, 미로그인, DB 실패, 누락 SQL, 관리자 권한, 안전 복구 경로 포함.
- 격리 PostgreSQL 검사 6그룹 통과: 재실행, 기존 데이터 불변, 초기 SQL 컬럼 교정 및 미확인 버전 거부, KST 가입 범위, 중복/쌍방 집계, 권한, 프로필 삭제, 취소, 빈 코호트.
- 기존 매칭 회귀 326건 통과.
- 로컬 실제 React 브라우저 20개 시나리오: 360/1280px 통계/기간 변경/늦은 응답/SQL 없음/실패/문의 복사 거절/민감 URL/재시도 연타/중복번호 안내/통계 전송 실패 중 OTP 재확인·완료. 실제 운영 요청 0.
- 기존 통합 작성 실제 브라우저 검사를 통계 API가 항상 실패하는 상태로 재실행: 한글 임시저장, 단계 오류, 사진·동의, 부분 성공 재시도, 연타 방지, 계정 격리, 조회 실패, 저장 공간 제한 모두 통과.
- 최종 production build 및 타입 검사 통과. 새 기능 대상 lint 오류·경고 0. 기존 매칭·사진 업로드·OTP·결제 백엔드 변경 없음.
- 검사 중 SQL 오픈카드 소유자 컬럼을 기존 DDL/API와 대조하여 owner_user_id로 정정하고, 이 일치 조건을 회귀 검사에 추가했다.

## 운영 반영 점검 — 2026-09-23

- 운영에는 초기 버전의 통계 테이블/함수가 이미 존재했다. 읽기 전용 검사에서 집계 함수의 오픈카드 소유자 참조 `c.user_id`로 인해 1/7/30일 조회가 모두 42703 오류임을 확인했다.
- `onboarding_funnel_owner_column_fix.sql`로 해당 참조 한 줄만 `c.owner_user_id`로 교정했다. 알려진 초기 함수 본문 해시만 허용하며, 알 수 없는 버전이면 중단한다. 함수 OID/ACL/소유자/보안 설정 등 본문 외 모든 pg_proc 속성이 같지 않으면 트랜잭션을 롤백한다. 이미 교정된 버전은 재실행 시 변경하지 않는다.
- 운영에서 교정 성공을 확인했다. 이후 서비스 권한의 읽기 전용 1/7/30일 집계 요청이 모두 HTTP 200 및 앱의 응답 스키마 검증을 통과했다. 비로그인 집계 요청은 401/42501로 차단되며 데이터가 반환되지 않았다.
- 새 테이블 RLS 활성화, anon/authenticated 조회·입력 차단, 집계 함수 실행 차단, 고정 코드 CHECK/복합 PK/프로필 삭제 CASCADE를 운영 카탈로그에서 확인했다.
- 기존 회원/매칭/결제/OTP 데이터 및 권한은 변경하지 않았다. 실제 문자 발송·결제 승인·프로필 등록 테스트는 하지 않았다.
