# 반복 후보 부분 교체 운영

## 적용 순서

1. `supabase/sql/dating_1on1_partial_refresh_monitor.sql` 설치. 새 설정은 기본 OFF이며 기존 모드를 바꾸지 않는다.
2. 해당 커밋을 배포하고 READY 및 운영 점검을 확인한다.
3. 관리자 일일 점검에서 자동 복구, 반복 후보 부분 교체, 복구 안내 메일을 켠다. SQL로 설정할 때도 이 순서를 지킨다.
4. 중지할 때는 `dating_1on1_refresh_monitor_settings.mode='off'`로 바꾼다. 후보를 되돌리거나 횟수를 차감하지 않는다.

## 대상과 처리

- 15분마다 최대 8건씩 처리한다. 최근 7일 새로고침 이용자를 한국 날짜 기준 하루 한 번 점검한다.
- 현재 후보 절반 이상을 이전 목록에서 실제로 본 기록이 있을 때만 부분 교체를 검토한다. 현재 목록을 다시 열어본 것만으로 반복 판정하지 않는다.
- 일반 추천과 같은 차단·숨김·회원 상태·성인 여부·중복 계정 필터를 사용한다. 최근 활동만으로 후보를 제외하지 않는다.
- 나이 조건에 맞고, 지역 중심점 기준 90km 이내이며, 교체하는 기존 후보보다 멀지 않은 미노출 후보를 가까운 순으로 최대 3명 넣는다. 동거리에서는 최근 등록을 우선한다.
- 최근 30일 노출·저장 목록·추가 지역 열람·기존 요청 상대는 새 후보로 쓰지 않는다. 대안이 없으면 유지한다.
- 추가 후보, 숨겨서 빈 자리, 찜·요청·진행 중 매칭은 건드리지 않는다. 저장 목록과 현재 화면이 다르거나 조회가 불완전하면 건너뛴다.
- 이용자가 동시에 새로고침하거나 지역·나이·프로필 상태를 바꾸면 저장하지 않는다. 회원별 교체 간격은 최소 24시간이며 수동 복구도 포함한다.

## 횟수와 안내

- 교체 이벤트는 `rotation_only=true`, `quota_refunded_at`이 있는 무료 이벤트로 기록한다. 기존 유료·기본·보너스 사용 기록은 유지한다.
- 후보 저장, 무료 이벤트, 개인 알림, 메일 대기 기록은 한 트랜잭션이다. 아무것도 바뀌지 않았거나 저장이 실패하면 안내도 생기지 않는다.
- 메일은 오전 9시~오후 8시 전까지 기존 매칭 알림 수신 설정을 따르고, 발송 직전 실제 저장 목록을 다시 확인한다. 그사이 후보가 바뀌면 보내지 않는다.
- 발송 예약과 고유 중복 방지 키를 사용한다. `sent`는 발송 서비스 접수 상태이며 수신함 도착을 뜻하지 않는다. `unknown`은 거부 설정 또는 불확실한 결과일 수 있으므로 자동 재전송하지 않는다.
- 결제·번호 공개·매칭 상태를 수정하는 쿼리는 포함하지 않는다.

## 검증

`node --test scripts/check-partial-refresh.cjs scripts/check-partial-refresh-sql.cjs`로 후보 규칙, 중복 실행, SQL 동시 변경 방어, 권한, 실패 시 전체 롤백, 횟수 보존을 확인한다. `node scripts/check-critical.cjs`는 기존 추천·매칭·결제·번호 공개까지 포함한다. 관리자 화면 검사는 `node scripts/check-refresh-monitor-browser.cjs`다.
