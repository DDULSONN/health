# 일반 검수: 욕설·성적 문구·부실 소개 확인

관리자 `일반 검수`의 문구 탐지 보강이다. 등록 차단, 자동 숨김·삭제·밴, 연락처 공개, 인증, 결제, 추천 로직에는 연결하지 않는다.

## 검사와 표시

- 기존 검수 대상(오픈카드, 유료카드, 1:1 카드 및 각 지원 내역)에 공통 적용한다.
- 작성자의 이름/닉네임, 직업, 소개, 강점, 이상형을 검사한다. 1:1 지원의 상대 이름·상대 ID, 인스타 계정 필드는 이 욕설·성적 문구 검사에서 제외한다.
- 성적 행위·만남 제안, 음란물·노골적 성적 표현은 `high`, 컵 사이즈 등 성적 신체 강조는 `medium`으로 관리자 확인을 요청한다. **정책 위반 확정이 아니다.**
- 성적 사유 하나만 있어도 기본 목록에 표시한다. 사유에 해당 필드명을 붙인다.
- 기존 앞 500자 절단을 2,000자로 늘려 현재 소개/이상형 입력 범위의 뒤쪽도 검사한다.
- 전각, 일부 구분기호·공백·제로폭 문자 우회도 정규화한다. 일반 운동/체형 표현, 성적 지향 자체, 즉각적인 거절 문구는 오탐을 줄인다. 규칙 기반이라 모든 은어·문맥을 완벽히 판별하지 못하며 관리자의 최종 판단이 필요하다.
- AI 검수를 추가로 실행해도 일반 검수의 더 높은 위험도와 사유가 사라지지 않는다.

### 은어 보강 (sexual-slang-v2)

- 성적 만남·대화 은어(섹친, 폰섹, 캠섹, 영섹, 초대남, 쓰리썸 등), 성적 사진/영상 요구, 성인용품·노골적 표현을 추가한다.
- `ㅅㅅ`, `ㅅㅍ`, `ㅇㄴㅇ`, `ㄴㅋ` 등 초성은 가능/파트너/구함 등 문맥이 함께 있을 때 검사한다. `ㅅㅅ!` 같은 응원 표현이나 `69`, `성향`, `파트너`, `밤 운동`만으로 성적 문구라고 판단하지 않는다.
- 기존 공백·기호·제로폭 문자 우회에 더해 일부 숫자 치환(`섹1스`, `s3x`, `p0rn`), 한글 자모 분리, 영문 밑줄 경계도 처리한다. 제한된 규칙이므로 모든 우회나 은어를 탐지하지는 못한다.
- 감지 단어를 검수 사유에 최대 24자로 함께 표시한다. 전체 소개나 상대의 정보는 사유에 복사하지 않는다. 실제 등록된 원문은 접기 없는 `프로필 내용` 영역에 항목별 한국어 제목과 함께 바로 표시한다. 줄바꿈과 긴 문구의 자동 줄바꿈을 유지한다.
- `폰섹 안 해요`, `no FWB` 등 바로 이어지는 거절은 구분하되 성적 신체 조건으로 상대를 배제하는 문구는 검수 대상으로 남긴다. 운동·낚시·정액권/정액제·직업 관련 일반 문구의 오탐 회귀 사례를 검사한다.
- 관리자 일반 검수 경로에만 적용한다. 입력 차단, 자동 밴, 공개 순서·추천·번호 교환·인증·결제 동작에는 추가 연결하지 않는다. 기존 등록글은 재검수가 필요하다.

## 욕설 확인 (sexual-slang-and-profanity-v3)

- 한글 욕설·비하 표현과 영문 욕설은 `high`, 뜻이 애매할 수 있는 `ㅅㅂ`, `ㅂㅅ`, `ㅈㄹ` 등 초성은 `medium` 검수 사유로 표시한다. 사유가 하나뿐이어도 기본 검수 목록에 나온다.
- 공백·일부 기호·제로폭 문자·전각 문자를 정규화하고 `씨.발`, `병1신`, `f**k`, `sh1t` 등 제한된 우회 표현도 검사한다. 감지한 필드와 단어를 사유에 함께 표시한다. 모든 우회 표현을 탐지한다는 뜻은 아니다.
- `시발점`, `도시 발전`, `질병 신호`, `전염병`, `새끼손가락`, `class` 등 정상 단어·문구는 회귀 테스트로 보호한다. 단독 `새끼`, `미친` 같은 문구는 이 규칙만으로 욕설이라고 단정하지 않는다.
- 욕설을 인용하거나 거절하는 문장도 단어 기반 확인 대상으로 남을 수 있다. **욕설·괴롭힘 확정이나 자동 제재가 아니며**, 관리자가 원문과 문맥을 확인한다. 모호한 초성도 같은 원칙으로 판단한다.
- AI가 낮은 위험도로 판정해도 일반 규칙의 사유와 더 높은 검수 위험도는 유지한다. 기존 게시물은 일반 검수를 다시 실행해야 새 규칙이 적용된다.
- 관리자 일반 검수에만 연결한다. 프로필 저장 조건, 기존 닉네임·게시글 필터, 사진, 공개 순서, 추천, 결제·번호 공개·인증은 변경하지 않는다. DB 구조 변경이나 별도 외부 API 호출도 없다.

## 부실 소개 확인

- 오픈카드는 `내 강점`이 소개 역할을 한다. 1:1 카드·지원 및 오픈/유료카드 지원은 `자기소개`를 검사한다. 유료카드는 자기소개가 비어 있으면 오픈카드에서 복사된 `내 강점`을 소개로 판단한다.
- 소개 역할 필드의 글자가 8자 미만이면 확인 대상으로 표시한다. 공백·기호·이모지·숫자·단독 자음/모음은 길이를 채우는 데 쓰지 않는다. 나이·직업·계정 ID·상대 정보·긴 이상형 문구를 소개 길이에 합치지 않는다.
- 인사말만 있는 글, `작성 예정`/`나중에 작성할게요` 등 임시 문구만 있는 글, 자음·숫자·기호만 있는 글, 4회 이상 반복된 짧은 문자/문구가 전체의 60% 이상인 글도 표시한다. 소개 외 강점·이상형에도 명백한 반복/임시 문구는 검사하지만 짧은 이상형 조건에는 8자 기준을 적용하지 않는다.
- `배려하며 잘 웃어요`처럼 간결하고 기준 길이를 충족하는 소개는 부실 소개로 표시하지 않는다. `QA 테스트 업무를 합니다`나 정상 소개 뒤의 웃음 표현은 테스트/반복이라는 이유만으로 잡지 않는다. 기존 전체 텍스트의 단순 `테스트` 부분일치·반복 문자 규칙을 이 항목별 검사로 교체한다.
- 한 가지 사유만 있어도 `medium`으로 기본 목록에 나온다. 공개 순서·추천 순서·등록 조건은 바꾸지 않는다. 의미를 완전히 이해하는 판정기가 아닌 관리자 검수 보조이므로 최종 판단은 관리자에게 있다.

## 기존 게시물

배포 후 대상을 선택해 **일반 검수**를 다시 실행하면 해당 대상의 저장 결과가 갱신된다. 전체 회원을 소급 변경하지 않는다. 현재의 최신순/검사 건수 제한은 유지되므로 오래된 게시물은 대상 종류와 검사 건수를 조정해야 한다. `최근 검수 목록`에서는 화면에 불러온 구형/내용 변경 일반 검수 결과만 현재 원문으로 메모리에서 재평가한다. 목록 조회는 DB에 쓰지 않으며 전체 회원 재검사를 시작하지 않는다. 기존 AI 사진 검수 결과는 현재 사진과의 비교값이 없으면 명시적 재검수가 필요하다.

SQL 변경, 새로운 외부 서비스, 자동 메일 발송은 없다. 일반 검수는 AI 호출을 하지 않는다. DB 조회/기록과 앱 실행 비용까지 0이라는 의미는 아니다.

## 정상 확인과 중복 검수 제외

- `✓ 정상 확인`은 **현재 카드/지원 내역의 확인한 내용과 검수 사유**에 대한 관리자 확인이다. 회원 전체를 검사에서 제외하지 않으며 실제 카드 공개·매칭 상태도 변경하지 않는다. 서버 저장이 확인된 뒤에만 화면에서 숨긴다.
- 같은 내용을 다시 검수해도 기본 목록에서는 제외한다. `정상 확인 목록`에서 확인 시각을 보고 `정상 확인 취소`로 되돌릴 수 있다. 정상 확인 기록은 관리자들이 공유한다.
- 이름/닉네임, 작성자 소개·강점·이상형·직업 등 검사 항목과 사진 경로, 카드/작성자 식별자를 SHA-256으로 비교한다. 내용·사진을 변경하거나 새 카드/지원 내역을 등록하면 다음 검수에서 다시 판단하고, 의심 사유가 있을 때 기본 목록에 표시한다. 수정 자체만으로 의심 항목으로 올리지는 않는다.
- 단순 대기→공개 상태 전환, 검사 시각, 만료되는 사진 서명 URL, 상대방 이름은 확인 취소 사유가 아니다. 사진 업로드가 새 경로를 생성하고 기존 파일을 덮어쓰지 않는 현재 업로드 방식을 전제로 한다.
- 검수 규칙 버전과 사유 집합도 비교한다. 규칙 보강이나 AI 사진 검수에서 새 사유가 생기면 이전 일반 검수 확인으로 가리지 않는다. AI의 사유 표현이 달라져 재확인이 필요할 수 있으며, 요약 문구·사유 순서만 바뀐 것은 무시한다.
- 확인 시 서버가 현재 프로필과 저장된 검수 결과를 다시 비교한다. 보고 있던 내용이나 사유가 바뀌면 `409`로 거절한다. 확인 이후 수정된 내용은 이전 확인 기록과 일치하지 않는다. 취소는 확인 ID까지 일치해야 하므로 오래된 화면에서 다른 관리자의 새로운 결정을 지우지 않는다.
- 일반 검수 결과와 정상 확인 기록은 별도 테이블이다. 재검수 저장이 사람의 확인을 덮어쓰지 않는다. 확인 기록 조회 실패/DB 설정 미적용 시 의심 항목을 숨기지 않고 경고와 비활성 버튼을 표시한다. 확인 저장 실패 시에는 항목을 유지하고 해당 항목 안에도 오류를 표시해 재시도할 수 있다.
- 최근 결과는 한 번에 최대 50개 표시한다. 사진/프로필을 읽기 전에 확인 기록을 비교하며, 한 요청당 검수 기록은 최대 250개까지만 읽는다. 뒤쪽에 남은 항목은 `다음 결과 더보기`로 이어서 조회한다. 검사 실행 건수와 기존 최신순 대상 선정은 유지한다.

### 적용 순서와 검증

1. `supabase/sql/admin_dating_review_confirmations.sql`을 운영 DB에 한 번 적용한다. 새 테이블만 추가하며 기존 회원/카드/매칭 테이블은 수정하지 않는다. 반복 실행도 가능하다.
2. 앱을 배포한다. 구형 일반 검수 결과는 조회 시 현재 원문을 기준으로 확인용 비교값을 준비하므로 전체 재검수 없이 정상 확인할 수 있다. 확인 시 해당 일반 검수 결과를 먼저 저장하고 정상 확인을 기록한다. 현재 원문을 찾지 못하거나 구형 AI 검수인 경우 확인을 허용하지 않는다.
3. 정상 확인 → 최근 결과/재검수에서 제외 → 정상 확인 목록에서 취소 동작을 확인한다. 프로필 변경 자동 감시나 전체 회원 백그라운드 검사는 추가하지 않는다.

테이블은 RLS를 활성화하고 `anon`/`authenticated`/`PUBLIC`의 접근 권한을 제거한다. 관리자 검증을 통과한 서버에서만 `service_role`로 조회·저장·취소한다. 확인/취소 시 기존 관리자 감사 로그에도 남긴다.

`npm run check:admin-review-confirmation`은 UI 클릭·오류 응답·중복 클릭·잘못된 대상 응답·오래된 응답 덮어쓰기 방지 및 실제 라우트의 여섯 대상 확인/취소·재검수·수정·재등록·관리자 권한·조회 제한을 검증한다. `REVIEW_TEST_PGLITE_PATH` 또는 `REPORT_TEST_PGLITE_PATH`에 설치된 PGlite 모듈 경로를 지정하면 PostgreSQL 엔진에서 SQL 반복 실행, 권한, 제약 조건, 확인 ID 비교 취소도 검사한다. 이 테스트는 운영 DB를 사용하지 않는다.

### 2026-09-16: 자동 검수와 정상 확인 복구

- 원인: 일일 1:1 자동 검수가 비교값 없는 `rules_cron` 결과로 기존 수동 검수를 덮어쓰고 있었다. 카드 ID를 지원 ID로 재사용한 가짜 지원 검수 행도 함께 생성했다.
- 수동/자동 검수가 `lib/dating-profile-review.ts`의 동일한 정규화·규칙·내용 비교값을 사용한다. 자동 검수의 기존 최신 1,000개 제한과 실행 일정은 유지한다. 내용과 규칙 버전이 같으면 쓰기를 생략해 수동 AI 결과와 정상 확인을 유지한다.
- 자동 검수는 실제 `one_on_one` 카드 결과만 기록한다. 기존 `one_on_one_application` + `rules_cron` 조합은 DB 페이지 조회 단계에서 제외한다. 기존 기록을 삭제하지 않고 실제 지원서 검수는 유지한다.
- 자동 검수와 구형 결과 정상 확인 저장은 기존 검수 ID/시각을 비교해 갱신한다. 그 사이 새 수동 검수가 저장됐으면 덮어쓰지 않는다. 신규 자동 결과도 중복 키가 생기면 수동 결과를 보존한다.
- 자동 저장은 200개 단위 신규 등록, 동시 10개 기존 행 갱신, 갱신 시간 제한으로 묶는다. 관리자 정상 확인, 회원 상태, 매칭, 결제, 알림 테이블을 자동 수정하지 않는다.
- 내용 수정·재등록은 다음 검수 시 새 비교값으로 판단한다. 전체 프로필 실시간 감시를 추가한 것은 아니다. 원문이 삭제/조회 실패한 항목과 사진 비교값 없는 과거 AI 검수는 임의로 정상 확인하지 않는다.
- 검증: UI/관리자 밴/문구/정상 확인/자동 검수 회귀 테스트 **504개 통과**, SQL 권한 테스트 포함·건너뜀 없음. 분리한 HEAD 작업 사본에서 `next build --webpack` 성공. 운영 DB는 GET/HEAD만 허용한 로컬 라우트 재현으로 1:1 카드·오픈카드·실제 1:1 지원 목록 모두 200 응답 및 정상 확인 스냅샷을 확인했다. 운영 회원을 정상 처리하거나 검수 데이터를 쓰는 테스트는 하지 않았다.
- 운영 확인 테이블은 이미 존재하므로 이번 수정에 새 SQL은 필요하지 않다. 다른 환경에 테이블이 없으면 위 적용 순서의 기존 SQL이 필요하다.

## 수동 계정 밴

검수 결과의 `계정 밴`은 자동 판정이 아니라 관리자가 직접 실행하는 조치다. 오픈카드·유료카드·1:1 카드 및 지원 결과 모두 작성자 계정을 대상으로 하며, 지원 상대방 계정을 대상으로 하지 않는다. 밴 사유 입력과 이름·계정 ID·영향 범위 최종 확인을 거쳐 기존 `/api/admin/users/ban`으로 요청한다.

기존 관리자 권한, 관리자 자신/다른 관리자 계정 밴 방지, 감사 기록, 카드 내리기 동작을 재사용한다. 저장된 회원이 없는 경우 성공으로 처리하지 않고, 계정 밴 후 일부 카드 내리기가 실패하면 경고를 표시한다. 현재 화면의 같은 계정 결과에는 `밴 완료`가 함께 표시되며, 밴 해제는 기존 회원관리에서 한다. 표시가 아닌 실제 계정 상태는 기존 회원관리에서 확인할 수 있다.

`npm run check:admin-review-ban`은 오프라인 가상 데이터로 확인·취소·사유 검증, 중복 클릭, 작성자 식별, 오류 응답, 기존 밴·해제 경로를 검증한다. 실제 회원에게 밴을 실행하지 않는다.

## 문구 검증

`npm run check:dating-text-review`

실제 라우트를 오프라인 DB/AI 대역으로 실행한다. 여섯 대상의 탐지·저장·기본 목록 재조회, 500자 뒤 문구, 욕설·초성·우회 표현과 정상 단어, 부실 소개·정상 예문·길이 경계, 유료카드 선택 입력, 재검수 시 결과 갱신, 관리자 권한, 기존 연락처 탐지, AI의 위험도 하향 방지를 검증한다. 회원·매칭 테이블 쓰기, 외부 통신, 메일 발송은 허용하지 않는다.
