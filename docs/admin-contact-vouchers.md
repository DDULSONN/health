# 관리자 1:1 교환권 지급

위치: 마이페이지 → 관리자 → 회원관리 → 회원 검색 → **1:1 교환권 · 지급 / 내역**.

- 1회 1~10장, 지급 사유 5~300자. 확인 화면의 닉네임·회원 ID·수량을 확인한 뒤 지급한다.
- 기존 교환권에 추가된다. 사용 전까지 유지하며, 오픈카드 지원권과는 다르다.
- 미인증·이용 제한·탈퇴 회원은 새로 지급할 수 없다. 지급 직전에 회원 상태와 닉네임을 DB에서 다시 확인한다.
- 교환권 지급은 결제·매칭·번호 공개 상태를 변경하지 않는다. 사용 시에는 기존 교환권의 쌍방 수락·번호 인증·차단·중복 결제 검사를 그대로 거친다.
- 지급 사유, 수량, 회원, 관리자, 지급 요청 ID를 기록한다. 같은 요청 ID의 재시도는 다시 지급하지 않는다.

## 통신이 끊겼을 때

**같은 요청으로 지급 확인**을 누른다. 요청은 전송 전에 브라우저 세션 저장소에 보관되므로 새로고침 후에도 복원된다. 결과가 불명확할 때 다른 창에서 새로운 지급을 만들지 않는다. 별도 요청 ID로 새 지급을 확인하면 별도의 지급이다.

지급 완료 후 조회만 실패했다면 **내역 다시 확인**만 누른다. 회원 상태 변경으로 지급 자체가 거절되었다면 내역을 새로 조회하고 다시 확인한다.

## 설치·중단

`supabase/sql/contact_care_manual_vouchers.sql`이 이미 설치된 프로젝트에서 `supabase/sql/contact_care_admin_grants.sql`을 적용한 뒤 앱을 배포한다. 새 SQL 미설치 시 화면은 지급을 비활성화한다.

운영 중 긴급 중단은 새 지급 함수의 서버 실행 권한만 회수한다. 기존 교환권·지급 기록을 삭제하거나 기존 사용 함수를 변경하지 않는다.

```sql
revoke execute on function public.grant_contact_care_manual(uuid,uuid,uuid,integer,text,text) from service_role;
```

## 검사

- `node --test scripts/check-admin-contact-vouchers.cjs` — 입력, 관리자 권한, SQL 원자성, 재시도, 지급 수량, 기존 데이터 유지, API 조회/지급.
- `node scripts/check-admin-contact-vouchers-browser.cjs` — 확인/취소, 이중 클릭, 통신 실패·새로고침 복구, 회원 변경, 저장소 오류, 모바일 화면.
- `node scripts/check-critical.cjs` — 전체 회귀 검사. 새 지급 검사는 이 검사에도 포함된다.

테스트는 가상 회원·로컬 PostgreSQL을 사용하며 실제 지급·결제·메시지 발송을 하지 않는다.
