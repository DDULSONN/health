# 짐툴 운영 점검

## 매일: 관리자 → 오늘 처리할 일

- 승인 후 교환 확인은 **확인할 후보**다. 주문과 매칭이 맞는지, 이미 공개됐는지, 차단·취소되지 않았는지와 결제사 상태를 기존 처리 화면에서 확인한다. 건수만으로 환불·번호 공개·재결제를 시키지 않는다.
- 오래된 대기 건은 생성 후 24시간이 지난 앱 주문이다. 실제 청구 여부와는 다르다. 결제사 조회가 불확실하면 교환권·번호 공개를 대신 실행하지 않는다.
- 해당 항목이 `확인 필요`이면 0건으로 취급하지 않는다. 조회 오류와 대상 없음은 구분한다.
- 신고를 통한 밴도 일반 회원관리 밴과 같은 범위의 공개 카드를 내린다. 일부 카드 정리에 실패하면 신고를 미처리로 유지하고 해당 회원의 카드 상태부터 확인한다.
- 홍보 메일은 미리보기와 실제 발송의 대상이 달라질 수 있다. 새로 수신 거부했거나 동의를 확인할 수 없는 계정은 발송에서 제외된다. 필수 매칭 알림 동작은 이 규칙과 별개다.
- CSV 내보내기에서 이름·연락처·자유서술은 비운다. 업무용 식별자와 상태는 남으므로 외부에 공유해도 되는 익명 자료는 아니다. 개별 기록은 기존 권한이 있는 처리 화면에서 확인한다.

## 배포 전후

1. 어떤 커밋이 배포되는지 확인하고, `npm run check:critical` 및 영향을 받는 브라우저 검사를 완료한다. 운영 배포와 미리보기 주소를 혼동하지 않는다.
2. 운영 DB를 바꾸지 않고 `supabase/sql/admin_operations_release_readiness.sql`의 지표를 확인한다. 감사 테이블이나 회원 직접 주문 쓰기 권한 항목이 거짓이면 별도 승인으로 보완한다. 로컬 기능 코드가 이 문제를 덮거나 권한을 완화하지 않는다.
3. 배포 전후 `node scripts/check-operations-smoke.cjs https://api.helchang.com`을 명시적으로 실행하면 공개 페이지와 비로그인 관리자 차단을 읽기 전용으로 점검한다. Cloudflare 확인 화면이나 네트워크 차단이라면 정상 사용자 브라우저에서 따로 확인한다.
4. 격리된 테스트 계정으로 기존 로그인·프로필 수정 복귀, 수락된 매칭의 번호 가림, 결제 승인/혜택 구분, 이미 완료된 교환·교환권 표시, 차단된 후보 숨김을 본다. 운영 결제를 발생시키지 않는다. 화면과 실제 운영 API가 같은 커밋을 사용 중인지 확인한다.
5. 로그인 갱신 실패·번호 공개 오류·업무 집계 실패가 배포 직후 증가하면 트래픽 규모와 함께 확인한다. 권한 검증 실패 또는 기존 정상 계정 경로 차단 시 확대를 중단하고 해당 배포 기능을 먼저 되돌린다. 이전 코드가 권한을 더 약하게 만들면 SQL·보안 조치는 되돌리지 않는다.

## 정기 점검

- 로그인 장애: Google/Apple 설정의 확인 담당자와 만료 알림(30·14·7일 전)을 관리한다. 새 가입만 성공했다고 판단하지 말고 기존 테스트 계정에서 예전 프로필·매칭이 이어지는지 확인한다. 비밀번호·키·실회원 연락처는 로그나 배포 기록에 남기지 않는다.
- 백업: DB 복구와 프로필 사진 저장소 복구를 따로 확인한다. 운영을 덮어쓰지 않고 격리 환경에서 최근 백업의 관리자 업무 목록·기존 매칭·결제 연동 상태를 검증하고 복구 소요 시간과 백업 시점을 기록한다.
- 위 절차는 사람 또는 승인된 기존 배포 파이프라인에서 실행한다. 이 변경에 운영 자동 스케줄·외부 알림·DB 마이그레이션 적용은 포함되지 않는다.
